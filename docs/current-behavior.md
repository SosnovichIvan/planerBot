# planerBot: реализованное поведение

Срез кода: 2026-10-17, ветка `fix/event-removal-mobile-ui`.
На момент подготовки на VPS установлен `0.1.7`; описанное ниже новое удаление
и UI-исправления ещё не выпущены. Эта инструкция описывает код,
а не гарантирует версию конкретного окружения. Новое управление темами отложено
по решению владельца. Номера релизов проверяются по Git-тегу и образам контейнеров.

Это основной справочник текущей функциональности. [Матрица приёмки](acceptance.md)
связывает её с тестами; [запуск тестов](testing.md) описывает границы проверок.
`requirements.md`, `architecture.md` и `implementation-plan.md` сохраняют контекст
требований/плана, но не являются доказательством реализации отложенных функций.

## 1. Назначение и роли

Бот собирает события из подключённых Telegram-групп и предоставляет персональный
Mini App. Если человек состоит в А и Б, запуск из А позволяет смотреть оба чата.
Само место запуска не даёт дополнительных прав. В общий чат не отправляется
персональный список событий других чатов.

| Действие | Участник | Администратор целевого чата |
| --- | --- | --- |
| Календарь, карточка, ссылка сообщения | Только доступные ему чаты | То же, без доступа к чужим чатам |
| Приду / Не приду / сброс ответа | Да, для активного события | Да |
| Количества ответов | Только после собственного ответа | То же правило, без исключения |
| Создание, правка, удаление из календаря | Нет | Да |
| Импорт сообщения по тегу или /event | Нет | Да, от личного аккаунта |
| Подтверждение импорта, повтор публикации | Нет | Да |
| Настройки чата | Нет | Да |
| Сообщение группе ответивших | Нет | После своего ответа, для активного события |
| Личное разрешение на ЛС | Управляет своим разрешением | То же |

`can_manage` определяет кнопки, но не заменяет серверную авторизацию. Сервер
повторно проверяет членство пользователя и права бота в целевом чате. Администратор
А не получает полномочий в Б. При ошибке проверки доступ закрывается, а не
разрешается из кэша. Уже увиденные пользователем сведения технически не отзываются.

## 2. Подключение и открытие

1. Назначить бота администратором группы. Обновление `my_chat_member` регистрирует
   чат и общий поток; обязательного `/setup` нет.
2. Для forum-чата темы обнаруживаются по сообщениям и сообщениям создания/
   переименования темы. Bot API не перечисляет автоматически все старые темы.
   `/setup Название` в нужной теме остаётся способом явной регистрации.
3. Бот добавляет `/calendar`, а администраторам также `/event` и `/settings`.
   Отправляет reply-клавиатуру «Календарь» и сообщение со ссылкой открытия.
4. `/calendar`, `/start`, `/settings` или текстовая кнопка «Календарь» присылают
   сообщение с «Открыть мой календарь». Ссылка `t.me/...?...startapp=...` запускает
   настроенный Main Mini App. URL приложения задаётся в BotFather отдельно.
5. В обычном браузере без Telegram initData показана инструкция входа; демо-входа
   и production bypass нет.

**Ограничение Telegram:** текстовая reply-кнопка отправляет текст боту и не
превращена в прямое открытие Mini App. Компактная кнопка меню рядом с input в
группе не реализована и не обещается. Для открытия используется ссылка сообщения
или Main Mini App. Кнопка menu/private и reply-клавиатура группы — разные механизмы.

Вход: заголовок `Authorization: tma <initData>`. Backend проверяет HMAC,
дубли параметров, размер, ID, время подписи (TTL по умолчанию 300 секунд;
допуск будущего времени 30 секунд). `start_param` — только навигационная подсказка.
Ошибки подписи/сессии дают 401 и предложение открыть приложение заново.

## 3. Календарь

- При первом открытии тема тёмная независимо от оформления Telegram.
  Переключатель сохраняет выбор в localStorage текущего устройства.
- Сверху: бренд, настройки для администратора, переключатель темы; рядом
  «Создать событие» для администратора и кнопка обновления. Лишнего вводного
  текста над сеткой нет.
- Селект «Чат» показывает доступные чаты и «Все чаты». Фильтров темы/тега в UI нет.
  Членство определяет сервер, frontend не пытается получить чужие данные.
- Месяц переключается стрелками; сетка начинается с понедельника. Даты и время
  событий показываются в часовом поясе их чата, не переводятся в timezone устройства.
- Пустое состояние отличается от ошибки. Обновление повторяет запрос событий.
  Изменение чата/месяца очищает устаревший scope; незавершённые fetch отменяются.
- Высота клеток фиксирована и не зависит от названий/числа событий.
  Красный маркер и текст «Нужен ваш ответ» обозначают активные события без ответа.
  Индиго-маркер/«Обновлено» обозначает непросмотренные правки; оба признака независимы.
- Одна встреча в дне открывает карточку. Несколько — drawer со списком, затем
  карточку поверх него. Escape закрывает только верхний слой и возвращает фокус.
- API возвращает максимум 200 событий за запрос и `has_more`. В этом случае
  показывается предупреждение, рекомендуется конкретный чат. Даже одна видимая
  встреча открывает список с предупреждением, а не выдаёт его за полный день.
- Удалённые (`cancelled`) события не попадают в сетку, повестку и лимит 200.
  Невыполненные удаления сообщений показываются только администраторам отдельной
  очередью вне повестки: до 50 задач, независимо от выбранного месяца.
- Многодневное событие попадает в затронутые дни; окончание ровно в 00:00 не
  добавляет лишний день. API-диапазон: начало включительно, конец исключительно,
  не более 62 дней.

## 4. Создание события

Администратор открывает форму, выбирает управляемый чат и включённую тему.
В обычной группе внутренний поток имеет ID 1 и название «Чат»; публикация идёт
без `message_thread_id`. В forum-чате используется выбранный Telegram thread.
Создание/удаление новых тем из приложения **не реализовано и сейчас вне scope**.

| Поле | Реальное правило |
| --- | --- |
| Название | Обязательно, 1–120 символов |
| Дата начала | Обязательна |
| Время | Необязательно; отсутствие начала означает весь день, время окончания без начала нельзя |
| Окончание | Если задано — строго позже начала; для другой даты нужно время окончания |
| Часовой пояс | Из настройки чата, по умолчанию UTC; явно показан в форме |
| Формат | Офлайн / онлайн / гибридная; сам по себе не меняет правило места/ссылки |
| Место / адрес / карта / подключение | Достаточно любого одного; все четыре пустыми быть не могут |
| Место / адрес | До 120 / 300 символов |
| Ссылки | До 400 символов; http/https, host, без credentials/пробелов |
| Описание | До 1200 символов |
| Теги | До 8, `#слово`, до 32 символов после #, нормализация регистра и дублей |
| Приглашение в ЛС | Необязательная галочка, по умолчанию выключена |

Суммарное содержание карточки ограничено 3600 UTF-16 units. Невозможное или
неоднозначное местное время при DST отклоняется с понятной ошибкой. Новые события
требуют места/ссылки; `place_pending` оставлен для совместимости со старыми данными.
Ввод отдельных геокоординат отдельным контролом не реализован.

Дата и 24-часовое время выбираются в оформленных окнах. «Весь день» отключает
поля времени и отправляет `null`. Чат/тема — оформленные селекты. Выбор, крестик,
Escape и (после #22) нажатие на фон закрывают селект без закрытия самой формы.
Отмена выбора не меняет значение. Для закрытия грязной формы требуется подтверждение.

Высота формы явная, учитывает `--tg-viewport-height` с fallback `100dvh`.
Заголовок и нижние действия не прокручиваются вместе с полями. Прокрутка есть
у области полей; крестик имеет размер 44×44. Проверки браузерных размеров не
заменяют проверку клавиатуры и safe area в Telegram iOS/Android.

Сохранение создаёт событие и публикационное задание в одной транзакции. Успех API
значит «сохранено», а не «Telegram уже доставил». Ключ `Idempotency-Key` стабилен
для повторов одного создания. Ошибка валидации сохраняет черновик; при сетевом
неизвестном исходе поля блокируются и повтор отправляет то же тело с тем же ключом.
Повторное создание с новым ключом может создать дубликат — сначала обновить список.

## 5. Создание из Telegram и импорт

`/event` без многострочного тела отправляет ссылку формы с контекстом чата/темы.
В личке это общий вход в создание; права выбранного чата всё равно проверяются.
`/event` с многострочным телом и сообщения/подписи медиа с настроенным тегом
обрабатываются структурированным парсером, а не AI и не пошаговым мастером.

```text
#событие #команда
Название: Встреча
Дата: 20.10.2026
Время: 19:00–20:00
Место: Кафе
Адрес: Москва
Формат: Офлайн
Описание: Планы команды
```

Распознаются также ISO-дата, `Окончание`, `Карта`, `Ссылка`. Неизвестные/повторные
поля, некорректные даты и времена отклоняются, свободный неоднозначный текст не
угадывается. Автор должен быть администратором от личного аккаунта. Сообщения
ботов и анонимного `sender_chat` не импортируются. Парсер не создаёт дубли из
собственной карточки. Чат/тема берутся из сообщения, не из произвольного текста.

Тег регистронезависим. Команда /event сохраняет активное событие; импорт по тегу
при включённом «Подтверждать импорт администраторов» создаёт `pending`.
Повторы update не создают вторую запись; более старые edits не перетирают новые.
Правка исходного сообщения обновляет существующее событие. Удаление Telegram-
сообщения автоматически не отслеживается: отмена выполняется явно.

## 6. Правка, обновления, отмена и публикация

- Редактировать можно незавершённое отменой событие при актуальной версии.
  Чат/тема фиксированы; перенос — новое событие и отмена старого.
- Конфликт версии даёт 409; черновик не исчезает, нужно обновить данные.
- Галочка уведомления при каждом открытии редактора выключена, даже если при
  создании отправлялись приглашения. Явное включение требует подтверждения.
- Реальная правка повышает версию и обновляет карточку, опубликованную ботом.
  Без изменения полей версия не повышается и рассылка не создаётся.
- Голоса не сбрасываются. Предыдущие поля сохраняются в `event_revisions`,
  личная просмотренная версия — в `event_seen`. Непросмотренность не зависит
  от localStorage или голосования.
- Получение карточки отмечает её версию просмотренной. «Что изменилось» показывает
  изменения от последнего просмотра; повторное открытие сохраняет описание
  последней правки. Просмотр администратором не убирает маркеры у остальных.
- «Удалить событие» требует подтверждения. API `/cancel` сохраняет статус
  `cancelled`, историю и голоса, но убирает встречу из календаря. Worker удаляет
  сообщение Telegram, а не заменяет текст на «Отменено». До первой публикации
  он не создаёт новую карточку. Для удалённого события RSVP и рассылки недоступны.
- Удаление сообщения асинхронное. Отказ/неизвестный исход видны администратору
  отдельно от повестки; повтор не создаёт новую карточку. Если ID неизвестен
  после неудачной первой отправки, нужна ручная проверка чата, не ложный успех.
- Telegram допускает удаление сообщений младше 48 часов при необходимых правах.
  Старое сообщение/отказ в правах остаётся ошибкой очереди, событие в календарь
  не возвращается. [Контракт deleteMessage](https://core.telegram.org/bots/api#deletemessage).

Статус события: `pending`, `active`, `cancelled`. Несохранённый черновик живёт
только в UI, отдельного серверного `draft` нет. `source`: `form`, `bot`, `message`.

Отдельные статусы публикации: `pending` → `sending` → `published` / `failed` /
`unknown`. Worker повторно проверяет права автора и доступность темы. Нет прав —
`failed`; определённый отказ Telegram — `failed`; неизвестный исход — `unknown`.
Зависший `sending` после lease 60 секунд становится `unknown`, не отправляется
вслепую. Для `failed` доступен ручной повтор; `unknown` требует подтверждения
риска дубликата. Для pending/sending UI обновляет список каждые 3 секунды.

Для `source=message` отдельная карточка не создаётся: календарь ссылается на
исходное сообщение, бот не редактирует его при правке. Явное удаление события
администратором ставит именно исходное сообщение в очередь удаления (с теми же
ограничениями Telegram). Worker создаёт/обновляет карточки источников `form` и
`bot`, в том числе многострочной команды /event.

## 7. RSVP и группы

Для активного события доступны «Приду» и «Не приду». Пользователь меняет ответ
или сбрасывает его в «Не проголосовал». До собственного yes/no API возвращает
`counts: null`, UI не показывает количества. Правило одинаково для участника
и администратора. После сброса количества снова скрываются.

Аудитория — **зарегистрированные участники календаря**, а не полный состав
Telegram-группы. Запись создаётся при посещении календаря/карточки; выход из
чата обрабатывается membership update, перед выдачей/отправкой доступ проверяется
снова. Bot API не предоставляет полный каталог всех участников для массовой ЛС.

Администратор после своего ответа нажимает группу «Приду», «Не приду» или
«Не проголосовали». Форма сообщения открывается вторым modal поверх карточки.
Текст: 1–1500 символов. После подтверждения создаётся очередь; в ЛС добавляется
ссылка на событие в приложении. Закрытие непустого черновика требует подтверждения.
Ошибка не стирает текст. При неизвестном исходе повтор использует исходные тело
и ключ; создание с другим ключом — другая рассылка, возможны повторы.

Кнопка проверки доставки показывает количества `pending`, `sending`, `sent`,
`skipped`, `failed`, `unknown`. Очередь — не подтверждение доставки каждому.
Worker сверяет актуальные членство/права, активность события/темы, регистрацию,
разрешение на ЛС и текущий ответ. Изменившие группу ответа или вышедшие из чата
пропускаются. Неизвестный исход автоматически не повторяется. Для временного
отказа проверки/FloodWait отложенный повтор ограничен пятью попытками.

## 8. Разрешение личных сообщений

«Разрешить сообщения» вызывает `requestWriteAccess` Telegram, если доступен.
Положительный callback не считается сохранённым серверным разрешением: UI
предлагает «Обновить разрешение» или /start в личке. Backend учитывает подписанное
`allows_write_to_pm`, private `write_access_allowed` update и личную /start.
При отказе или старом клиенте показана инструкция /start, ложного успеха нет.

«Отключить уведомления» и личная `/stop` выключают ЛС для пользователя глобально.
Обычное повторное посещение календаря не отменяет этот opt-out; повторная личная
`/start` включает сообщения. Блокировка бота учитывается membership update.
Администратор не может выдать разрешение за другого человека.

Галочка приглашения при создании и явное уведомление при правке создают рассылку
`all` только зарегистрированной аудитории с последующей проверкой согласия.
Утверждение «всем участникам чата в личку» без этих ограничений неверно.

## 9. Настройки и ограничения

Настройки показываются только для управляемых чатов текущего выбора. В них:
IANA timezone, тег события, подтверждение импорта, включённые известные темы.
Версия настроек предотвращает потерю параллельных изменений. `creation_policy`
в API/UI зафиксирован `admins`. Отключение темы не удаляет её или сообщения:
участники не видят её события, администраторы видят их для управления, новые
создания/доставка в выключенную тему не разрешены.

Не реализованы: CRUD тем из приложения, произвольный AI-разбор, пошаговый мастер
бота, плановые напоминания по времени до события, повторяющиеся события,
Google/ICS-подписки, список всех Telegram-участников, физическое стирание истории/RSVP,
универсальная кнопка Mini App рядом с input группы. Не обещаются SLA, RPO/RTO,
полная WCAG-сертификация и совместимость каждого Telegram-клиента без приёмки.

## 10. API и эксплуатация

Актуальная схема: [backend/openapi.json](../backend/openapi.json), frontend типы
генерируются из неё. Все календарные ответы `Cache-Control: no-store`.

| Метод и путь | Назначение |
| --- | --- |
| GET /health/live, /health/ready | Процесс и доступность БД; не подтверждают доставку Telegram |
| GET /api/me | Подписанная identity |
| GET /api/chats?after=… | Доступные чаты, страницы по 25 |
| POST /api/calendar/visit | Регистрация аудитории календаря |
| DELETE /api/calendar/notifications | Глобальный opt-out ЛС |
| PUT /api/chats/{chat}/settings | Настройки с version |
| GET /api/events?start=…&end=…&chat_id=… | До 200 событий; topic_id/tag. Отдельные removals/has_more_removals — только управляющим администраторам |
| POST /api/chats/{chat}/events | Создание с Idempotency-Key UUID |
| GET /api/chats/{chat}/events/{id} | Карточка, RSVP и личная прочитанная версия |
| PUT /api/chats/{chat}/events/{id} | Изменение с version |
| POST …/{id}/approve, …/{id}/cancel | Подтверждение/удаление из календаря с version |
| POST …/{id}/retry | Ручной повтор; ack_duplicate_risk для unknown |
| PUT …/{id}/response | yes / no / unanswered |
| POST …/{id}/campaigns | audience, text, Idempotency-Key UUID |
| GET …/{id}/campaigns/{campaign} | Агрегаты доставки, только управляющий администратор с ответом |

401 — нет корректной сессии; 403 — нет полномочий; 404 — объект не найден в
указанном чате; 409 — версия/повтор/состояние конфликтуют; 422 — некорректные
данные; 503 — нельзя проверить доступ/готовность. Network error отличается от
определённого отказа: результат мутации может быть неизвестен.

PostgreSQL хранится в постоянном volume. Схема: 0001 — чаты/темы, 0002 — события/
публикации, 0003 — RSVP/контакты/рассылки, 0004 — правки и личные просмотры,
0005 — очередь удаления старых отменённых сообщений без стирания данных.
API, polling и worker — отдельные процессы, Telegram идёт через закрытый прокси
без прямого fallback. Gateway отдаёт HTTPS-статику и разрешённые API.
Публичный webhook в production не включён; используется один polling.

Выпуск: рабочая ветка → develop → main → неизменяемый MAJOR.MINOR.PATCH-тег
на main → проверки → release.sh. Перед миграцией останавливаются writers,
сохраняется закрытый pg_dump. База не очищается; production downgrade/restore
автоматически не выполняются. [Инструкция эксплуатации](deployment.md) и
[прокси](telegram-proxy.md) содержат команды и recovery-ограничения.
