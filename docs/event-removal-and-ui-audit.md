# Удаление события и аудит UI — 2026-10-17

Источник визуальных ограничений: существующий Open Design проект planerBot,
`brand-spec.md`, `ui-components.css`, актуальный `planerbot-prototype.html`;
согласованная палитра/ритм 4–8 px сохранены. Новый визуальный preset не вводится.
Этот документ описывает изменения рабочей ветки, не утверждает их установку на VPS.

## Подтверждённые дефекты и контракт

1. `/cancel` менял статус, но общий список продолжал отдавать отменённые встречи.
   Теперь они исключаются **до** календарного limit 201/выдачи 200 и не занимают
   места активных событий. День/повестка обновляются после удаления.
2. Worker заменял текст сообщения на «Отменено». Теперь удаляет известную карточку,
   а для импорта — исходное сообщение. Отмена до первой отправки ничего не публикует.
   Уже отсутствующее сообщение считается выполненным удалением, повтор не создаёт новое.
3. Программный фокус заголовка попадал под глобальную focus-рамку. Неинтерактивный
   heading остаётся фокусируемой точкой входа для screen reader, без рамки.
   У кнопок/полей/ссылок клавиатурный focus **сохранён**, а не отключён глобально.
4. Прокрутка фокуса и времени могла двигать внешнее окно; padding сверху селекта
   не резервировал область focus indicator. Теперь скроллится только владелец,
   выбранный пункт виден полностью. Время ограничено доступной высотой landscape.
5. В некоторых последовательностях Chromium группировал native dialog и Escape
   закрывал несколько окон. Один обработчик верхнего слоя предотвращает native
   grouped cancellation; busy не закрывается, фокус возвращается к триггеру.
6. Личные уведомления/форма рассылки использовали боковые margins у кнопок.
   Вместо них flex-wrap/gap; у создания/правки/рассылки закреплены действия,
   скроллится тело. На ширине менее 360 px действия занимают полную ширину.

Удаление — логическое для БД: `cancelled`, ревизии, личные просмотры и RSVP
сохраняются. Это не GDPR-стирание и не физическое уничтожение записи.
Telegram: `deleteMessage` требует возраст меньше 48 часов и необходимые права.
Отказ не выдаётся за успех; задача показывается администратору отдельно от
повестки, с повтором. Если первая отправка дала unknown без message_id, нельзя
угадать сообщение: UI требует ручной проверки и не разрешает ложный автоповтор.
[Первичный источник ограничений](https://core.telegram.org/bots/api#deletemessage).

## Данные и SQL

Новых таблиц/индексов нет. Сохраняются PK/FK/версии/lease существующего outbox.
Удаление сохраняет статус и задание одной транзакцией с блокировкой Event.
Telegram вызывается worker после commit; сетевой вызов не держит транзакцию.
Известный отказ → failed, неопределённый исход → unknown. Удаление разрешено
также из выключенной темы, но текущие полномочия администратора/бота проверяются.

Repository list: три SELECT независимо от числа встреч: ID (201), joined выдача
(≤200), joined административные removals (51 → 50 + has_more_removals).
Последние не фильтруются месяцем, иначе старая ошибка исчезала бы из управления.
Tenant scope строится из проверенных admin_ids, участнику removals не возвращаются.
Подстановок пользовательских строк в SQL нет. На сервисном уровне RSVP/seen
добавляются ограниченными пакетными запросами, не по одному на событие.

`test_legacy_backfill_batches_and_preserves_unknown_work` выполняет реальные
EXPLAIN ANALYZE/BUFFERS на PostgreSQL тестовой БД: 501 cancelled + 1 active,
2 чата/2 темы, после ANALYZE. Один локальный прогон, тёплый cache:

| Вариант | Строк на выходе Limit | Execution ms | Shared hits / reads |
| --- | --- | --- | --- |
| Контроль без фильтра cancelled | 201 | 0.329 | 33 / 0 |
| Agenda с фильтром cancelled | 1 | 0.103 | 33 / 0 |
| Административная очередь | 51 | 0.102 | 111 / 0 |

Контроль — тот же SQL/параметры с неограничивающим условием вместо фильтра статуса;
это сравнение семантики прежней выборки, не benchmark production.
План содержит сортировку/seq scan для маленькой таблицы и joins по существующим
ключам; это не основание принудительно требовать index scan. Нагрузка/планы на
миллионах записей не измерены. Нужен повторный EXPLAIN при росте пилота, не обещание SLA.

## Миграция 0005 и восстановление

Это data-only backfill: legacy cancelled/published становятся pending; cancelled
без публикации получают задание, для source=message сохраняется исходный ID.
Active, RSVP и pending/sending/failed/unknown задания не стираются и не заменяются.
Проход — UUID cursor, по 500 строк, без OFFSET, ON CONFLICT с условием статуса.
Cursor внутри migration transaction: сбой откатывает транзакцию, повтор безопасен;
это не online backfill с отдельным durable checkpoint.

Rollout — штатное окно обслуживания: остановить **всех** writers, закрытый pg_dump,
upgrade 0004→0005, затем только новый API/bot/worker. Миграция берёт row locks на
перезаписываемых заданиях; zero-downtime и нулевые блокировки не обещаются.
Проверены пустой upgrade и заполненный upgrade со старой опубликованной карточкой,
импортом, активным событием/RSVP; отдельный тест проходит 501 запись и повтор.
Структура схемы совместима, но **старый worker нельзя запускать** с очередью
удаления: он опубликует «Отменено». Recovery — forward fix; downgrade data-only
не воскрешает сообщения и не удаляет задания. Дамп БД не восстанавливает уже
удалённое Telegram-сообщение. В production эту миграцию в рамках разработки не запускали.

не являются доказательством реального удаления: сетевой adapter и outbox проверены
pytest, реальная удаляющая команда в рабочий чат ради теста не отправлялась.
