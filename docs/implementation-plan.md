Технический план предложен 2026-10-15. Чекбоксы отражают фактическое выполнение;
наличие документа не означает реализацию приложения.

## 1. Проверка Telegram и каркас

- Проверить запуск Main Mini App по ссылке из группы в целевых клиентах.
- Проверить права, getChatMember, my_chat_member/chat_member и идентификаторы тем.
- Определить процесс обнаружения чатов пользователя и регистрации старых тем.
- Закрепить версии Python/Node, aiogram/FastAPI/React, Tailwind CSS и менеджеры зависимостей.
- Создать backend, frontend FSD, локальный PostgreSQL и Docker Compose.
- Настроить Tailwind CSS, общие дизайн-токены и светлую/тёмную тему Telegram.
- Добавить миграции, конфигурацию без секретов, CI lint/types/tests/coverage,
  проверку направления PR и изоляции FSD.

Приёмка: тестовый бот подключён к двум группам; одна кнопка открывает
персональные сессии двух пользователей; недействительный initData отклоняется.

## 2. Чаты, темы, членство

- Настройка чата администратором, timezone, теги, политика авторов и темы.
- Единая серверная проверка просмотра и управления конкретным объектом.
- Список доступных чатов без раскрытия неподтверждённых названий.
- Реакция на выход участника, исключение и потерю прав бота.

Приёмка: участник А/Б видит оба чата, участник только А — один;
подмена ID и старая кнопка не раскрывают Б; сбой проверки закрывает доступ.

## 3. События через календарь и бот

- Схема события, валидация времени, timezone, место/адрес/карта/онлайн-ссылка.
- Форма и диалог создания, выбор управляемого чата и зарегистрированной темы.
- Черновик, создание, редактирование, отмена и контроль версии.
- Outbox публикаций, ссылка на карточку, retry для известных отказов,
  состояние unknown для неоднозначного результата отправки.

Приёмка: создание из А для Б публикует сообщение в выбранной теме Б;
двойной submit создаёт одно событие; отказ Telegram сохраняет событие.

## 4. Парсинг сообщений

- Разбор текста и caption по настроенному тегу и строгому формату полей.
- Проверка автора, разрешённой темы, неоднозначных дат и места.
- Уточнение и подтверждение, идемпотентный импорт, edited_message.
- Защита от повторного импорта собственных публикаций бота.
- Согласовать поведение при снятии тега с уже импортированного сообщения.

Приёмка: оба пути дают одну модель события; повторный update и редактирование
не создают второй записи; неверная дата не приводит к молчаливой публикации.

## 5. Персональный календарь

- Месяц, день, список ближайших событий, переход между периодами.
- Фильтры чата/темы/тегов и отметка источника каждого события.
- Детали с местом встречи, временем и ссылкой на сообщение.
- Административные действия доступны по фактическим серверным правам.
- Loading, empty, error, access denied, узкие экраны, клавиатура и focus.

Приёмка: групповой вход открывает персональную выдачу; события Б не появляются
в общих сообщениях А; следующая загрузка после выхода из Б исключает его данные.

## 6. Напоминания и пилот

- Одно настраиваемое групповое напоминание в исходную тему.
- Изменение/отмена события пересчитывает или отменяет ожидающее задание.
- Наблюдаемость webhook, outbox и reminder lag без содержания личных сообщений.
- Retention, резервные копии и проверка восстановления.
- Пилот на двух чатах и пользователях с разным набором членств.

Приёмка: корректное восстановление после перезапуска worker, отсутствие
напоминаний отменённого события, проверенные частичные сбои и изоляция данных.

## Перед первым релизом

Защита веток и обязательные проверки активны; frontend/backend имеют отдельные
отчёты минимум 90% строк и ветвей, миграции проверены на PostgreSQL.
PR идут в develop, затем develop → main. Публикация запускается только по
неизменяемому тегу MAJOR.MINOR.PATCH, входящему в историю удалённой main.
Релизные workflows и их проверки появятся с исполняемым приложением.
