# Техподдержка в боте

Срез кода: 2026-10-20, `feat/support-private-replies`. Последняя проверенная
production-версия — 0.1.9 с приёмом обращений; описанные новые ответы и приватные
тексты ещё не выпущены. Получатель поддержки задаётся числовым SUPPORT_CHAT_ID;
его аккаунт не раскрывается пользователю в новых подсказках или ответах.

## Пользовательский сценарий

1. В личке боту отправить `/support` (также есть в меню команд).
2. Ответить на приглашение бота: описать действия, ожидаемый и фактический результат.
   Telegram ForceReply подставляет ответ; можно закрыть его, ничего не отправляя.
3. Бот сохраняет обращение и сообщает номер и **постановку в очередь**, не обещает
   фактическую доставку или срок ответа. Worker отдельно присылает владельцу текст,
   имя, ник (если есть), Telegram ID автора и номер обращения.

Можно сразу написать `/support Не открывается календарь`. В группе/теме команда
не отправляет обращение: бот даёт кнопку перехода в личку (`?start=support`).
Текст из аргументов команды в группе не копируется в поддержку и не повторяется
в ответе. Уже написанный пользователем в группе текст бот автоматически не удаляет.

Поддержка доступна обычным пользователям и администраторам, в том числе без
подключённых чатов: поломка проверки членства не должна закрывать обращение.
Анонимные отправители, аккаунты ботов и чужой private chat_id не принимаются.
Обычные сообщения, ответы другим ботам, forwarded-приглашения, сообщения групп,
редактирование старого сообщения и команды календаря не превращаются в обращения.

Только текст: 1–3000 UTF-16 единиц после trim, Telegram emoji могут занимать две.
Фото/файлы/voice/caption без text не принимаются. При ошибке ввода показывается
причина и новое приглашение. Не присылать пароли/токены: об этом есть предупреждение.
Приглашение проверяется как ответ именно этому боту, а не хранится в памяти процесса;
после перезапуска на него можно ответить. Произвольный следующий текст без reply
не захватывается. После отправки повторный ответ — новое обращение, не продолжение.

Владелец может ответить текстом через Telegram reply на карточку обращения в
личке боту, включая старые карточки. Ответ сохраняется в очереди, после чего
worker отправляет пользователю новое сообщение от имени бота, не forward/copy.
Ник и профиль владельца автоматически не прикрепляются. Приветствие использует
ник пользователя, при его отсутствии — имя, затем «Здравствуйте!».

Пример (между приветствием и завершением — введённый владельцем текст):

```text
Здравствуйте, @viewer!

Спасибо за сообщение. Проверяем описанную проблему.

Спасибо, что помогаете улучшать planerBot!
Присылайте пожелания и замеченные дефекты через /support.
С уважением, команда поддержки planerBot.
```

Ответ — 1–3000 UTF-16 единиц после trim; шаблон укладывается в лимит Telegram.
Произвольный текст владельца не редактируется: если он сам напишет свой ник,
он останется в тексте. Для нового обращения/пожелания пользователь вызывает
/support; обычный ответ на полученное приветствие не становится новым тикетом.
SLA, вложения, кабинет тикетов и команда повтора неизвестной доставки не добавлены.
Подробности прав, SQL, миграции и отказов: [support-replies.md](support-replies.md).

## Настройка получателя

`SUPPORT_CHAT_ID` — числовой положительный ID личного Telegram-аккаунта владельца,
не ник и не ID группы. Настройка приходит только из окружения, пользователь не
может подставить адресата в команду. Реальный ID в публичный репозиторий не кладём.
Владелец должен открыть бота и нажать `/start`, не блокировать его.
Отправка личному пользователю только по `@username` не поддерживается контрактом
[sendMessage](https://core.telegram.org/bots/api#sendmessage).

Локально — `.env`; на VPS — root-only `/etc/planerbot/runtime.env` (0600).
Compose передаёт поле процессам; validator принимает старый env без него,
`0` выключает приём (default), ник/отрицательное/пустое/вне 52-bit отклоняются.
Без настройки бот **не обещает** принять обращение: предлагает попробовать /support
позже, без личного контакта владельца.
Проверить аккаунт получателя до включения; переименование Telegram-ника не меняет ID.
Адресат фиксируется в записи при создании: смена env не перенаправляет старые обращения.

Меню лички устанавливается polling-процессом при запуске, не меняет кнопку Mini App.
В новых подключаемых группах /support добавляется в chat-scoped команды. Старые
групповые command scopes автоматически не переписываются: `/support` работает
и без пункта меню. `/start support` не включает личные рассылки событий.

## Данные и доставка

`support_tickets` — отдельная очередь, без FK на события и без доступа из публичного
API/календаря. Хранятся текст и данные для обратной связи; содержимое не попадает
в логи, тексты Telegram errors не выводятся пользователю. Сообщение plain text,
HTML/Markdown пользователя не интерпретируется; previews ссылок отключены.

Уникальность `(user_id, source_message_id)` предотвращает дубли при повторе update.
Не более одного нового обращения в минуту. Транзакционная advisory lock в отдельном
support namespace сериализует запросы одного user_id; другой пользователь не блокируется.
Replay не перезаписывает текст или получателя и не расходует лимит.

| Состояние | Значение |
| --- | --- |
| pending | Сохранено, ожидает отправки/разрешённого повтора после 429 |
| sending | Задание захвачено worker с UUID lease, сеть вне DB-транзакции |
| sent | Telegram подтвердил sendMessage |
| failed | Подтверждённый отказ или исчерпаны три попытки после 429 |
| unknown | Неопределённый сетевой исход или истёк lease 60 секунд |

Worker использует тот же настроенный Telegram proxy и timeout 10 секунд.
После 429 — до трёх попыток с retry_after (1–3600 секунд). Timeout/network/server
error **не** вызывает слепой resend: Bot API sendMessage не даёт идемпотентный ключ.
Истёкший sending тоже становится unknown, поздний finish не перезаписывает результат.
Повторная обработка sent/failed/unknown автоматически не выполняется. Не обещаем
exactly-once: сбой после фактической отправки до commit может оставить unknown.

При failed/unknown администратор проверяет Telegram и закрытые данные очереди;
пользовательский номер помогает найти запись. Warning содержит только UUID, не
текст/имя/ник. Для мониторинга — агрегаты `status,count(*)` в support_tickets.
Автоматические оповещения о состоянии доставки и очистка истории пока не реализованы;
история входит в защищённые DB backups. Перед расширением пилота нужна согласованная
политика retention/удаления и внешний мониторинг очереди.

## SQL и миграция

0006 (генерация Alembic из metadata) создаёт только новую таблицу, PK, unique,
CHECK и индексы `(user_id,created_at)` и `(status,next_attempt)`. Старые таблицы
не переписываются; backfill N/A. Индекс source unique служит replay lookup,
user/created — последней заявке для лимита, status/next — claim/поиску зависших.
Нет запросов по одному на участника и выгрузки всего календаря.

Submit: advisory SELECT, unique lookup, bounded latest LIMIT 1, INSERT в одной
транзакции. Replay: lock+lookup. Claim: UPDATE expired sending + SELECT LIMIT 1
FOR UPDATE SKIP LOCKED + UPDATE; finish: SELECT PK/lease/status + UPDATE.
Каждый сетевой вызов — после commit захвата, без удержания транзакции.

На локальной PostgreSQL 17 проверены реальные SELECT из service/claim через
EXPLAIN ANALYZE/BUFFERS: 1000 фиктивных заявок (50 пользователей, 5 pending,
остальные sent) + новая заявка пользователя 777, после ANALYZE. Один тёплый прогон:
source lookup 0.012 ms / 2 shared hits, latest 0.024 ms / 2 hits, claim 0.040 ms /
5 hits; на выходе каждого — одна запись, reads 0. Source/latest использовали
support_user_created (оптимизатор вправе предпочесть его unique индексу на этом
распределении); claim — support_pending и incremental sort. Это проверка
ограниченности/индексов, не production benchmark и не обещание SLA. План при
росте истории нужно перепроверять, не принуждать index scan на маленькой таблице.

Rollout: PR → develop → main → тег, остановка writers, закрытый pg_dump,
upgrade 0005→0006, новый API/bot/worker. До миграции новый worker не запускать.
Старый код не знает таблицы и не доставляет поддержку. Recovery — forward fix.
Down migration удаляет историю поддержки; **не применять в production**.
Для возврата приложения сохранить таблицу и выключить приём, предварительно
проверив совместимость; резервную копию восстанавливать сначала отдельно.

## Проверка

Локальный прогон 2026-10-19: 285 pytest-тестов passed (Python 3.12.14,
pytest 9.1.1, coverage.py 7.16.2). Весь авторский backend/src/planerbot:
99.94% строк и 98.73% ветвей, без исключения support-кода; новые support-модули
покрыты на 100%. Frontend не изменён; его покрытие не усредняется с backend.
Ruff, format, mypy, migration check и трассировка прежних 51 UI-сценария прошли.

`test_support.py`: PostgreSQL intake/реальные ограничения, параллельный replay и
rate limit, lease и восстановление после сбоя, бюджет 429, безопасные сетевые
ошибки, получатель snapshot и plain text, graceful cancellation.
`test_support_bot.py`: Dispatcher/Telegram Update, private/group/deep-link/ForceReply,
ошибочный ввод, отсутствие перехвата обычной переписки и существующих команд,
полный mocked sendMessage путь через настоящую PostgreSQL очередь.
`check_migrations.py`: пустая и заполненная цепочка, сохранность старых данных.
`test_deployment.py`: совместимость env и отказ некорректной настройки.

Сеть Telegram в тестах подменена: сообщений реальным пользователям не посылали.
После установки нужны ручные проверки в Telegram Desktop/iPhone с согласованными
аккаунтами: /support → reply → одно сообщение владельцу, inline-вариант,
group deep link, отсутствие ника, недоступный получатель. Пока ID получателя
не указан и реальная доставка не проверена, включение функции не подтверждено.
