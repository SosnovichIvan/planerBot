# Предложение архитектуры

Статус: proposed. Дата: 2026-10-15.
Пользователь согласовал сценарии; стек и технические механизмы ещё не утверждены.

## Выбор

Предлагается модульный монолит: Python, aiogram для Telegram, FastAPI для
Mini App API, PostgreSQL для состояния и фоновых заданий; React + TypeScript
с FSD для Mini App. Версии будут закреплены на этапе каркаса.

Альтернатива — TypeScript + grammY + HTTP framework: единый язык с frontend,
но преимуществ для известных сценариев пока не установлено. Микросервисы
потребовали бы сетевых контрактов и распределённого состояния без подтверждённой
необходимости. На старте достаточно одного backend и worker из того же кода.

## Границы и владельцы

| Модуль | Контракт | Данные | Разрешённые зависимости |
| --- | --- | --- | --- |
| Чаты | registerChat, registerTopic, updateSettings | chats, topics, settings | Telegram adapter |
| Доступ | authorizeView, authorizeManage, listAccessibleChats | memberships, sessions | Чаты, Telegram adapter |
| События | createEvent, reviseEvent, cancelEvent, listEvents | events, event_tags, revisions | Доступ, Чаты |
| Разбор | parseMessage → candidate/validationErrors | Связь источника с событием, минимальный исходный текст | Контракты Событий |
| Публикации | requestPublication, deliver, reconcile | publications, outbox | Снимки Событий, Telegram adapter |
| Напоминания | schedule, cancel, deliverDue | reminders | События, Чаты, Telegram adapter |

Входные adapters HTTP и Telegram вызывают application contracts; модули не
зависят от adapters. Telegram client реализует узкие порты. Чтение чужих таблиц
в обход владельца и циклы запрещены. Каждый модуль проверяется через контракт
с подменой внешних портов; persistence проверяется на PostgreSQL.

## Создание и публикация

1. Сервер проверяет Telegram-сессию, права администратора, выбранный чат и
   принадлежность темы этому чату. Доверять клиентскому `chat_id` нельзя.
2. Создание события и задания outbox выполняется одной транзакцией PostgreSQL.
   Повтор формы защищён ключом идемпотентности; конкуренция — ограничением UNIQUE.
3. Worker вне транзакции отправляет карточку в тему и сохраняет `message_id`.
4. Ошибка публикации не уничтожает событие. Интерфейс показывает отдельный
   статус доставки. Задание хранит версию события, чтобы старая карточка
   не перезаписала новую правку; операции одного события упорядочиваются.
5. После сетевого таймаута отправка могла состояться. Bot API не предоставляет
   универсальной транзакции с нашей БД или ключа идемпотентности sendMessage.
   Результат отмечается unknown; слепой повтор не обещает exactly-once.
   Нужен согласованный сценарий сверки/ручного повтора с предупреждением
   о возможном дубле. Это проверяется отдельным отказным тестом.

Исходное сообщение участника и опубликованная карточка бота — разные ссылки.
Собственные исходящие сообщения не запускают повторный импорт. Отмена сохраняет
историю и обновляет карточку бота. Чужой исходник остаётся под управлением автора.

## Авторизация и обнаружение чатов

В Mini App сервер проверяет подпись и срок действия Telegram initData и выдаёт
короткую сессию; ссылка запуска не доказывает личность или членство.
Проверка доступа применяется к спискам, деталям, фильтрам и операциям изменения.
Для строгого требования доступа на следующий запрос положительный кэш между
запросами не используется: `getChatMember` проверяет каждый чат перед выдачей,
внутри запроса проверки объединяются. Недоступный Telegram означает закрытый
доступ, а не выдачу по устаревшему кэшу. Цену этой модели проверим на пилоте.

Bot API не даёт список всех групп пользователя или полного состава группы.
Кандидаты — подключённые чаты, замеченные взаимодействия/обновления членства
и явно подключённые пользователем чаты. Для пилота допустима ограниченная
проверка всех зарегистрированных чатов; для большого каталога нужна стратегия
обнаружения без утечки названий. Таблица memberships — подсказка, не источник прав.
Бот должен быть администратором; потеря прав отключает выдачу данных до проверки.

Календарь открывается из группы через ссылку запуска Main Mini App с контекстом
чата. `startapp` — только подсказка фильтра. Конкретную конфигурацию BotFather
и поддержку клиентов необходимо проверить в первом техническом spike.
Не следует рассчитывать на `web_app` inline-кнопку, доступную лишь в личном
диалоге, как на универсальный механизм группового запуска.

## Данные и жизненный цикл

- `events` владеет структурированным состоянием; сообщение является источником
  или публикацией. Каждое событие принадлежит ровно одному чату и теме.
- Чат, тема и источник Telegram используют составную область идентификаторов.
  UNIQUE `(chat_id, source_message_id)` применяется только к импортируемым
  сообщениям. Формы имеют отдельный ключ идемпотентности.
- Telegram IDs хранятся в BIGINT. Тема уникальна внутри чата, display name
  не является идентификатором. Связь event → topic обязана сохранять chat scope.
- Моменты времени хранятся в UTC плюс IANA timezone; события на весь день —
  локальными датами с исключающей датой окончания. Часовой пояс отображается.
- Обычное удаление сообщения не считается гарантированным сигналом отмены.
  Импорт всей старой истории через Bot API не обещается.
- Старые темы регистрируются через команду в нужной теме и наблюдаемые сообщения;
  универсальная полная загрузка списка тем не предполагается.
- Сырые сообщения не попадают в логи. Срок хранения и удаление исходного текста
  должны быть определены до пилота; для парсинга сохраняется только нужный контекст.
- Полная схема, индексы, nullability, retention и миграции проектируются до DDL
  по реальным запросам и правилам database-engineering.

## Проверка и пересмотр

Приёмка — матрица сценариев из requirements.md, тесты изоляции чатов,
конкурирующих правок, повторных updates и частичных сбоев доставки.
Coverage исполняемого авторского кода — минимум 90% строк и ветвей отдельно
для backend и frontend. DDL проверяется сценариями на PostgreSQL.

Пересмотр архитектуры нужен при измеренных ограничениях проверки членства,
нагрузке outbox, требованиях независимого развёртывания или смене состава команды.
Recovery: повтор фоновых заданий по состоянию, восстановление PostgreSQL из
проверяемых backups, отсутствие автоматического удаления события при сбое Telegram.
