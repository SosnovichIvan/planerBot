# Контракт первого этапа

Исторический срез каркаса в PR №2. Актуальные события, настройки и доставка
описаны в [events-implementation.md](events-implementation.md).

Статус: каркас реализован и проверен локально; создание и парсинг событий
остаются следующими этапами. Приёмка в реальных Telegram-клиентах не выполнена.

## Вход и права

`/setup [название темы]` вызывается от личного аккаунта администратора внутри
темы forum-supergroup. Бот проверяет администратора и собственные права,
затем одной транзакцией upsert регистрирует чат и текущую тему. Повтор безопасен
для данных. Анонимный администратор должен отправить команду от личного аккаунта.
Существующие темы регистрируются отдельно командой в каждой нужной теме.
`my_chat_member` отключает ранее зарегистрированный чат после потери прав
администратора у бота. Права пользователей проверяются при запросе, поэтому
постоянная таблица состава групп и обработка всех `chat_member` пока не нужны.

`/calendar` и `/start` отправляют общую кнопку с Main Mini App deep link.
`startapp` содержит контекст, но не даёт права доступа и не ограничивает
персональный список только исходным чатом. В группе публикуется только кнопка.

Клиент передаёт исходный `Telegram.WebApp.initData` в заголовке
`Authorization: tma <initData>`. Сервер проверяет HMAC, дубликаты полей,
`auth_date` (TTL 300 секунд, допустимое опережение часов 30 секунд) и user.
Секрет не сохраняется в URL/localStorage. Простой режим каркаса не выдаёт
отдельных сессионных токенов: спустя TTL нужно открыть Mini App заново.
Долгая сессия с контролируемым обновлением — отдельная дальнейшая возможность.

## HTTP

Канонический контракт — FastAPI schemas и сгенерированный `backend/openapi.json`.
Frontend использует автоматически сгенерированные OpenAPI-типы.

| Endpoint | Вход | Результат |
| --- | --- | --- |
| GET /health/live | Нет | 200: процесс отвечает |
| GET /health/ready | Нет | 200: БД отвечает; 503: БД недоступна |
| GET /api/me | tma header | Проверенный пользователь; 401 при неверной/старой подписи |
| GET /api/chats | tma header, after | Доступные чаты/темы и next_cursor; 503 при невозможности проверки |
| POST /telegram/webhook | Update, secret header | 204 после обработки; 403 при неправильном секрете |

На всех ответах `Cache-Control: no-store`. Нет CORS для произвольных origins;
frontend и API размещаются за одним origin. Vite proxy используется локально.
Reverse proxy обязан ограничить тело webhook и не логировать Authorization.
Для `/api/chats` проверяются и права бота, и текущее членство пользователя
через Telegram, без положительного кэша между запросами. Ошибка хотя бы одной
проверки закрывает всю выдачу, без частичных метаданных.

На странице обрабатываются loading, вход вне Telegram, empty, 401, network/503,
retry, смена фильтра и переход месяца. Создания событий пока нет; интерфейс
показывает это явно, без неработающих кнопок и демонстрационных событий.

## Данные, запросы и миграции

PostgreSQL 17 (локально доступный образ 17-alpine). Новая пустая схема;
старого приложения/данных ещё нет. Используются обычные PK/FK и upsert,
без возможностей, специфичных для PostgreSQL 18.
Владелец таблиц — модуль чатов.

| Таблица | Потребитель и ключ | Обязательные поля | Связи и удаление |
| --- | --- | --- | --- |
| chats | register, list; BIGINT Telegram chat ID | title VARCHAR(256), active BOOLEAN | Один чат → много тем |
| topics | список тем; PK (chat_id, thread_id) | title VARCHAR(256) | FK chats, ON DELETE CASCADE |

Все поля NOT NULL; повтор регистрации обновляет название, не создаёт дубль.
Telegram ID уникален в своей области; thread_id уникален только вместе с chat_id.
Объём пока неизвестен. Пилот рассчитан на небольшой каталог, без обещаний SLA.

Список читает до 25 активных кандидатов в порядке chat_id после курсора
и темы этих кандидатов одним дополнительным запросом — без N+1 SQL. Для каждого
кандидата выполняется до двух сетевых проверок, параллелизм ограничен четырьмя.
Клиент перебирает страницы, показывая данные только после полного успеха.
PK chats покрывает equality/range/order-by; PK topics начинается с chat_id и
покрывает выборку тем. Дополнительных индексов без измерений не добавлено.
Планы и latency на реальном объёме пока не измерены.

`0001` создаёт две таблицы и FK в одной транзакции. Upsert чата и темы атомарен;
сетевые проверки выполняются до транзакции. Backfill не нужен. Downgrade
удаляет таблицы и данные, разрешён только в изолированной тестовой среде.
Для сохранения подключений после пилота нужен backup/forward fix.

## Дизайн

Навык ui-ux-design предложил flat-направление и календарную синюю палитру.
Маркетинговый landing pattern и serif body из выдачи не подходят рабочему
Mini App; выбрана компактная композиция «месяц + подключённые чаты», системный
sans-serif, общие Tailwind-токены, отдельная тёмная палитра.
На телефоне панели располагаются вертикально, на широком экране — рядом.
Поля имеют label, месячная сетка — table, ошибки — alert, загрузка — status,
кнопки минимум 44px с видимым фокусом. Telegram themeChanged обновляет тему.

## Проверка в Telegram (ещё не выполнена)

Нужны тестовый токен, Main Mini App с HTTPS URL и два тестовых чата с темами.
В BotFather настроить Main Mini App, добавить бота администратором в оба чата,
вызвать /setup в каждой нужной теме. Пользователь А состоит в обоих чатах,
пользователь Б — только в первом. Открыть одну и ту же кнопку /calendar:
А видит два чата, Б — один. После выхода А из второго чата открыть календарь
повторно: второй чат отсутствует. Потеря прав бота закрывает доступ к чату.
Проверить Android/iOS/Desktop отдельно. Автотесты с mock Telegram не заменяют
эту проверку на клиентах.
