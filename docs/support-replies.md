# Приватные ответы техподдержки

## Контракт до реализации

Пользователь вызывает /support без показа аккаунта владельца. Владелец отвечает
текстом через Telegram reply на доставленную ботом карточку обращения. Бот
отправляет пользователю новое сообщение: приветствие с его @ником (fallback —
имя, затем нейтральное приветствие), ответ без крайних пробелов и приглашение присылать
пожелания/дефекты через /support с подписью команды поддержки planerBot.
Forward/copy сообщения владельца не используется, parse_mode отключён.

Разрешён только private chat настроенного SUPPORT_CHAT_ID, совпадающий с
from_user.id. Reply должен ссылаться на сообщение этого же бота, без признака
пересылки, с фиксированным заголовком и UUID обращения. Адресат берётся только
из БД по UUID; user_id из текста не используется. В БД дополнительно проверяется
target_id обращения против текущего владельца. Это позволяет ответить и на ранее
отправленные карточки, где provider message_id не сохранялся. Обычные сообщения,
группы, боты, sender_chat, чужие/пересланные карточки не создают ответ.

Ответы на старые подсказки /support распознаются по стабильному началу сообщения
бота; новая подсказка и ошибки не содержат ника владельца. Подставленный вручную
в сам текст ответа ник не редактируется: отправляется дословный введённый текст.

## Данные и транзакции

Владелец данных — модуль support. Новая таблица support_replies: UUID PK,
ticket_id FK support_tickets (CASCADE при явном удалении обращения), sender_id,
source_message_id, body (1–3000 символов, дополнительно UTF-16 budget в сервисе),
created_at/next_attempt timestamptz, status, attempts, lease UUID, claimed_at.
Одна карточка имеет 0..N ответов; пока нет публичного API удаления/истечения.
Не добавляется доступ к календарям или требование согласия на рассылки событий:
это ответ на инициированное самим пользователем обращение.

UNIQUE(sender_id, source_message_id) защищает replay update, включая гонки.
INSERT ON CONFLICT с последующей сверкой ticket/body не позволяет подменить
содержимое повторного запроса. FK и CHECK закрепляют существование обращения,
положительные идентификаторы, длину и допустимые статусы/число попыток.
Проверка обращения и сохранение намерения — одна короткая транзакция, без сети.
Worker использует SELECT FOR UPDATE SKIP LOCKED LIMIT 1 и lease; сетевой вызов
вне транзакции. 429 ограничен тремя попытками, явный отказ — failed,
таймаут/сетевой неизвестный исход или устаревший lease — unknown без автоповтора.

Запросы: ticket PK → INSERT по unique source → при replay один PK/source lookup;
claim — один bounded reply плюс ticket PK. N+1 списка нет. Индексы: PK,
unique source, (status,next_attempt) для worker и ticket_id для FK/cascade.
Очередь предполагается небольшой; это не измерение production-нагрузки.

## Миграция и проверка

PostgreSQL 17, Alembic: аддитивная 0007 после 0006, без изменения старых строк
и backfill. Создание новой таблицы/индексов транзакционное; FK требует короткой
блокировки родительской таблицы, отсутствие блокировок не обещается.
Порядок выпуска: backup → upgrade → новый бот/worker. Старый код совместим с
добавленной таблицей, но ответы не обрабатывает. При откате кода новые задания
сохраняются для forward-fix; downgrade удаляет очередь ответов и не служит
безопасным восстановлением данных. Production в этой задаче не меняется.

Проверки: приватность текстов, fallback имени, owner/tenant/provenance,
параллельный replay, rollback/constraints на PostgreSQL, отказ/429/unknown,
потерянный lease, restart, полный путь Dispatcher → БД → worker → gateway
с подменённой сетью. Миграция на пустой и заполненной тестовой БД, планы запросов
и полный backend coverage ≥90% строк и ветвей. Реальные сообщения не отправляются.

## Тексты и состояния

| Триггер | Что сообщаем | Следующее действие |
| --- | --- | --- |
| /support | Описание проблемы и предупреждение не присылать секреты; получатель — команда, не личный ник | Reply на приглашение |
| Поддержка не настроена | Приём пока не настроен, попробовать /support позже | Не обещаем сохранение |
| Reply владельца сохранён | Номер ответа, очередь не подтверждает доставку, не повторять | Worker доставляет отдельно |
| Пустой/длинный ответ | Нужен текст 1–3000 UTF-16 единиц | Отправить корректный reply |
| Сбой записи/commit | Не удалось подтвердить сохранение; ответ мог попасть в очередь | Не повторять новым сообщением вслепую |
| Ответ пользователю | Приветствие → текст → благодарность, /support и подпись команды | Новые пожелания/дефекты через /support |

## Результаты проверки 2026-10-20

- Изолированная PostgreSQL 17.11, planerbot_test. Пустой upgrade и заполненный
  0001→0007 с обращением на 0006 проходят; Alembic check не находит schema drift.
  События/публикации/RSVP и старое обращение сохранены, новая очередь пуста.
- pytest 9.1.1: 336 тестов. Coverage.py 7.16.2 по всему backend/src/planerbot,
  без новых исключений: 99.94% lines / 98.81% branches. Новая очередь, изменения
  support.py/support_bot.py и gateway покрыты на 100%; worker сохраняет прежнюю
  непокрытую ветвь ожидания задачи. Команды: `.venv/bin/pytest -s` и
  `.venv/bin/python scripts/check_coverage.py`; переменная TEST_DATABASE_URL
  указывает только на изолированную planerbot_test.
- Ruff 0.17.0 check/format и mypy 1.20.2 проходят. OpenAPI не изменился.
- Реальные SELECT сервиса/worker проверены через EXPLAIN ANALYZE/BUFFERS:
  1001 фиктивный ответ, 6 pending до claim, остальные sent, после ANALYZE.
  Owner/recipient — support_tickets_pkey (0.008/0.007 ms, по 2 shared hits);
  replay — support_reply_source_unique (0.017 ms, 5 hits);
  claim — support_replies_pending + incremental sort/lock/limit
  (0.033 ms, 4 hits). На выходе каждого — одна строка. Это один тёплый локальный
  прогон, не production benchmark и не обещание SLA.
- Целевая проверка Dispatcher/БД/worker использует настоящую БД и mock Telegram;
  username/ID из пользовательского текста не определяет адресата. Проверены
  старые карточки, отсутствие nickname владельца в новых шаблонах, replay,
  отказы/таймауты/429, fallback имени, CASCADE/constraints и rollback.

Изменения логотипа/материалов портфолио остаются отдельными локальными правками
и не входят в PR поддержки. Production/согласия на рассылки не изменялись,
реальные сообщения и миграции на VPS не запускались. Приёмка в реальном
Telegram после согласованного выпуска остаётся отдельным шагом.
