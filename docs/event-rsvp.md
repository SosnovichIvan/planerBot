# Ответы на события и личные уведомления

Статус: accepted (состав участников согласован 2026-10-16).

## Контракт

Участник календаря — пользователь, открывший приложение, чьё текущее членство
в чате проверено сервером. Это не полный состав Telegram-чата. Боты исключены.
Один пользователь имеет один ответ на событие: yes/no; отсутствие ответа означает
unanswered. Сброс удаляет ответ. До собственного ответа статистика не выдаётся
сервером, в том числе администратору. Личные ответы не публикуются в общем чате.

Карточка события открывается внутри приложения; ссылка на сообщение отдельная.
Если в дне одно событие — сразу карточка; иначе список. Красный статус сопровождает
текст «Нужен ваш ответ». Отменённые/неподтверждённые события не требуют ответа.

Администратор после собственного ответа может написать группе yes/no/unanswered.
Перед отправкой показывается подтверждение. Задание идемпотентно по ключу
администратор+событие+ключ запроса; повтор с другим телом отклоняется.
Адресаты фиксируются при создании задания; перед доставкой снова проверяются
членство получателя, права отправителя и текущая группа ответа. Вышедшие,
заблокировавшие бота и сменившие ответ пропускаются. Сеть не вызывается в DB-транзакции.

Галочка при создании ставит в очередь уведомления известным участникам календаря.
Разрешение личных сообщений получается из подписанного Telegram initData либо
из личного /start. Флаг SDK callback сам по себе не доказывает разрешение.
Нет разрешения — адресат пропускается, пользователь видит способ включения.
Очередь ограничивает скорость; 429 откладывается, неизвестный исход не повторяется
автоматически (Bot API не даёт exactly-once sendMessage).

## Данные и границы

Модуль RSVP владеет участниками, контактами, ответами и заданиями рассылки.
Существующие EventService/ChatAccess остаются владельцами событий и авторизации.
PostgreSQL 17: participants (chat,user PK), contacts (user PK), responses
(event,user PK), campaigns (UUID PK, fingerprint), notices (campaign,user PK).
FK каскадируют при удалении чата/события; response ограничен yes/no.
Ответы и кампании сериализуются блокировкой строки события. Начальная рассылка
создаётся в одной транзакции с событием, только при первом создании.
notify_members — намерение первой отправки, не часть сохранённого JSON payload:
старый EventInput с extra=forbid продолжает читать новые события после отката.
Fingerprint без рассылки сохраняет прежний формат; с рассылкой включает намерение.

Индексы: PK participants по chat для аудитории, responses по event для подсчёта,
notices по status/next_attempt для claim; составной PK предотвращает двойную
постановку получателя. Выборки страниц/месяца ограничены; личные ответы месяца
загружаются одним запросом, не по запросу на событие.

## Поставка и проверки

Добавочная миграция 0003 не удаляет существующие события/публикации, не требует
backfill полного состава: его нет в Bot API. Старый код совместим с новыми
таблицами, старый payload получает defaults. Сначала миграция, затем API/bot/worker.
Откат приложения возможен с сохранением новых таблиц; downgrade удаляет RSVP,
поэтому не является штатным recovery. Перед production — штатный pg_dump.

Проверки: PostgreSQL upgrade с данными, конкурентные ответы/повторы кампаний,
скрытие статистики, межчатовая изоляция, снятие прав, Telegram outage, timeout,
429, запрет ЛС, смена группы до доставки; frontend loading/error/focus, одиночный
и множественный день, deep link, мобильный/широкий экран, coverage >=90% по проекту.
Рассылки проверяются с подменённым Telegram, не на реальных участниках.

## Отдельная форма рассылки (2026-10-16)

Нажатие администратором на группу ответов открывает второе native modal-окно
поверх карточки события. В заголовке — выбранная группа, ниже — событие/чат,
поле сообщения и отправка/отмена. Нижняя карточка недоступна до закрытия формы.
Escape закрывает только верхнее окно и возвращает фокус на кнопку группы.
При закрытии непустого черновика требуется подтверждение; ошибка отправки
не очищает текст. Неизвестный исход сохраняет исходные тело и ключ запроса.
После успешной постановки в очередь форма закрывается, статус виден в карточке.

Общий Modal учитывает несколько одновременно открытых окон: прокрутка страницы
восстанавливается после закрытия последнего, включая одновременный unmount.
Изменение UI не меняет API, авторизацию, очередь, схему БД или обработку разрешений
Telegram. Найденные дефекты разрешений/объяснения пропусков остаются отдельной задачей.

Проверки: 66 frontend-тестов (Vitest/V8 4.1.11), 99.33% строк / 94.27% ветвей
по всей src с прежними исключениями; TypeScript, ESLint/Steiger, build:check.
Chromium mock API: 375×812, 1280×900, 812×375, обе темы, reduced-motion,
150% корневой шрифт на 375 px. Проверены три группы, верхний modal, фокус,
Escape, подтверждение отмены, ошибки/повтор с тем же ключом и отсутствие overflow.
Просмотрены мобильный светлый, широкий тёмный и мобильный тёмный с крупным текстом.
Production не изменялся, реальные сообщения не отправлялись.
