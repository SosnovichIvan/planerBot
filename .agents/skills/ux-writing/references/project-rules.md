# Правила: ux-writing

Применяются при подключённом профиле `--project-rules standard` или явном
выборе владельца. Обязательные требования владельца не выдаются за стандарт
внешнего источника. Для существующего несовместимого проекта обозначь конфликт,
не меняй архитектуру без задачи на переход.

## Правила интерфейсных текстов

Создай таблицу состояние → сообщение → действие → реальный результат.
Различай пустые данные, отсутствие доступа, загрузку и ошибку. Текст кнопки
объясняет действие; успешное сообщение появляется после подтверждения системы.
Ошибка указывает проблему и доступный способ исправления, не обвиняет пользователя.

Форма имеет постоянную метку: placeholder не заменяет label. Ошибка связана
с полем; обязательность и ограничения доступны до отправки. Не передавай
смысл только цветом. Проверяй фокус/объявление динамического сообщения совместно
с реализацией. Для удаления объясни объект и последствия, если это требуется потоком.

Повторяемое значение — единый ключ/термин, но ключи разных контекстов не объединяй
автоматически: перевод и падеж могут различаться. Проверяй plural, даты, единицы,
длинный перевод и узкий экран. Покрытие прозы процентом не измеряется; готовность
проверяется матрицей реальных состояний и отсутствием неподтверждённых обещаний.
