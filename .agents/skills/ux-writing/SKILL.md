# UX writing

Напиши текст, который помогает выполнить действие и понимаемо объясняет
состояние системы. Работай независимо от design/development skills.

Восстанови flow: что пользователь сделал, что система знает наверняка, что
можно сделать дальше. Проверь реальные product rules, screenshot/component и
существующий glossary. Не додумывай наличие автосохранения, возврата денег,
поддержки, срока обработки или способа восстановления.

## Решения

- Название кнопки описывает действие и объект, если без объекта неоднозначно.
  В destructive confirmation действия различаются без чтения длинного текста.
- Для error объясни проблему и доступное исправление; не обвиняй пользователя
  и не показывай внутренний stack/error code вместо понятного сообщения.
- Разделяй неопределённый исход, подтверждённый отказ и успех. После timeout
  платежа не утверждай «деньги не списаны» и не предлагай повтор, если его
  безопасность не установлена продуктовым контрактом.
- Empty state отличается от ошибки и отсутствия результатов фильтра.
  Loading не обещает точное время без данных.
- Не скрывай нужную инструкцию только в placeholder, tooltip или цвете.
  Visible label и accessible name должны сохранять общий смысл.
- Для ограничения длины измерь текст; не обрезай смысл, единицы и критические
  условия ради arbitrary fit. Отметь конфликт лимита с понятностью.
- При локализации сохраняй placeholders, plural rules, форматирование и
  смысл действия. Не собирай предложение из переводимых кусочков, если
  грамматика целевого языка требует иной порядок.

## Результат и проверка

Для нескольких состояний верни таблицу: экран/ключ, состояние/триггер, текст,
действие пользователя и ограничение. Для одной кнопки достаточно готовой строки.
Раздели строки для продукта и вопросы о неустановленном поведении.

Пройди путь от действия к результату: не противоречат ли заголовок, описание,
CTA и следующее состояние. Проверь терминологию, placeholders, длины и статус
операции. Без render не утверждай, что строки помещаются на всех viewport.
Запрос текста не разрешает менять product rules или автоматически публиковать
переводы в внешней системе.

## Профиль правил проекта

Применяй [профильные правила](references/project-rules.md) только при явном согласии
на правила этого скилла в инструкциях проекта. При наличии approved snapshot
используй его; наличие файла само по себе не активирует правила. Они не запускают другие скиллы автоматически.
