# Backend review

Проверь последствия изменения на границах сервиса. Skill независим от других
skills. Запрос ревью не означает разрешение менять код или публиковать review.

## Контекст

Определи сравниваемые версии или модуль, runtime, transport, storage и требования.
Проследи путь входа через authentication, authorization, validation, бизнес-логику,
транзакцию и внешние эффекты. Читай вызывающий код и настройки middleware прежде,
чем объявлять отсутствующей защиту, которая может находиться выше по стеку.

## Анализ риска

- Identity: проверяется ли доступ субъекта к конкретному ресурсу и tenant;
  доверены ли входные claims; сохранён ли запрет при другом endpoint/worker.
- Контракты: wire-поля, error/status mapping, defaults, pagination и versioning;
  остаются ли прежние клиенты работоспособны во время смешанного rollout.
- Инварианты: конкурентный read-check-write, unique/conditional write, atomicity,
  isolation и границы rollback. Транзакция сама по себе не устраняет любой race.
- Повторы: idempotency scope включает владельца и смысл операции; сравнение
  payload, состояние in-progress, одновременные запросы и replay после сбоя.
- Внешние эффекты: timeout может означать неопределённый исход; проверь момент
  записи результата, ack и отправки. Для очередей/платежей/webhooks прочитай
  [distributed-effects.md](references/distributed-effects.md).
- Ресурсы: bounded concurrency, cancellation, connection/body cleanup,
  deadlines, graceful shutdown и обработка ошибок фоновой задачи.
- Эксплуатация: ограниченные metrics labels, отсутствие секретов в логах,
  совместимость config, поведение при недоступности dependency.

Проверяй только относящиеся к изменению пункты. Не требуй переписать простой
сервис в hexagonal architecture и не объявляй отсутствие отдельного слоя багом.
Для performance finding укажи наблюдаемую деградацию либо вход и механизм её
возникновения; количество строк кода не является доказательством.

## Подтверждение и результат

Для подозрения построй конкретную последовательность входов/сбоев и проверь
защитные условия. При доступном harness используй узкий regression/contract test
в изолированной среде; не вызывай реальные платежи, рассылки или production jobs.
Если тест недоступен, отделяй вывод по коду от выполненной проверки.

Каждое finding содержит приоритет, файл/строки, достижимое условие, нарушенный
контракт, последствия и доказательство. Используй шкалу проекта, иначе P1 для
серьёзного нарушения данных/доступа/основного сценария, P2 для условной регрессии,
P3 для малого влияния; P0 только для подтверждённого безусловного блокера.
Предлагай минимальное направление исправления, не обязательный redesign.

В diff-review findings относятся к внесённым изменениям; прежние проблемы
обозначай отдельно. Не считай гипотезу подтверждённым дефектом, не дублируй
одну причину. Заверши областью проверки, тестами и оставшимися неизвестными.
Пустой список findings допустим и предпочтительнее выдуманных замечаний.

## Профиль правил проекта

Применяй [профильные правила](references/project-rules.md) только при явном согласии
на правила этого скилла в инструкциях проекта. При наличии approved snapshot
используй его; наличие файла само по себе не активирует правила. Они не запускают другие скиллы автоматически.
