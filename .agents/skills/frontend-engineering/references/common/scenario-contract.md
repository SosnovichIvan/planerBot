# Контракт сценария

Читайте для формы, нового route, async UI или изменения server/client boundary.

До кода определи действие, входы, доступные роли, ответы API и достижимые
состояния. Сохрани соответствие server payload, cache identity и отображаемого
объекта: tenant/user/filter, влияющие на ответ, должны учитываться в принятом
механизме ключей и очистки кеша.

Для формы зафиксируй владельца draft, исходное значение, правила reset при
смене сущности, validation boundary, pending и повтор submit. Не сбрасывай
введённое при recoverable error. Optimistic update требует понятного rollback
и поведения при перекрывающихся mutations, а не только happy path.

Для async UI проверь два запроса с обратным порядком ответов, смену route и
unmount. Используй существующие cancellation/query механизмы; не дублируй их
самописным state, если гарантия уже обеспечена.

Для SSR проверь, какие данные доступны на сервере и в браузере, кто владеет
кешем и не делится ли пользовательский ответ между запросами. Проверь direct
URL, hydration и invalidation после mutation средствами текущего framework.

Для performance work сначала воспроизведи задержку и измерь относящийся к ней
показатель: render, network waterfall, bundle или interaction. Оптимизация
должна сохранять поведение; без замера не обещай процент ускорения.

Передача результата: критерий приёмки → реализация → выполненная проверка;
неизвестные API/design решения вынеси отдельно. Это контракт артефакта, а не
требование запускать другие skills.
