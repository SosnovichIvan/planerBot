# Frontend delivery checks

Читайте перед завершением реализации или при выборе достаточного набора тестов.

## Проверяемое поведение

- Acceptance criteria покрыты observable assertions, а не только snapshots.
- Component tests проверяют действия пользователя, доступные имена и состояния.
- Утилиты с ветвлением покрыты граничными и ошибочными случаями.
- API tests проверяют URL/method/payload, ошибки и cache invalidation.
- E2E покрывает критический изменённый путь, если проект располагает устойчивым
  окружением для него.

Не требуй одинаковый процент покрытия для любого проекта. Соблюдай repository
gate; при его отсутствии ориентируйся на риск изменённого кода и явно сообщай
непокрытые ветви.

## Минимальная последовательность

1. Запусти тесты изменённого модуля.
2. Запусти formatter/lint и typecheck штатными командами проекта.
3. Запусти production build или ближайший эквивалент.
4. Для UI проверь основной viewport и затронутые responsive состояния.
5. Проверь отсутствие generated drift, случайного нового lockfile и секретов.

## UI quality gate

- Проверь loading, empty, partial, error, disabled и success состояния, которые
  достижимы в изменённом сценарии.
- Проверь keyboard-only path, порядок focus, видимый focus indicator, accessible
  names и связь ошибок с полями.
- Проверь узкий и широкий viewport в пределах responsive matrix проекта.
- Для SSR проверь server render и hydration; для SPA — direct URL и fallback
  routing; для async route — отмену или игнорирование устаревшего ответа.
- Не заявляй pixel-perfect соответствие без визуального сравнения с источником
  дизайна на нужных состояниях и viewport.

Если команда отсутствует или инфраструктура сломана независимо от изменения,
не подменяй результат: зафиксируй точную команду, ошибку и что осталось
непроверенным.
