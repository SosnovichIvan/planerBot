# Правила: database-review

Применяются при подключённом профиле `--project-rules standard` или явном
выборе владельца. Обязательные требования владельца не выдаются за стандарт
внешнего источника. Для существующего несовместимого проекта обозначь конфликт,
не меняй архитектуру без задачи на переход.

## Формат ревью

Сначала установи требования, diff и область влияния. Каждое замечание содержит
файл/строку, конкретный путь выполнения, нарушенный контракт, последствия,
приоритет и способ воспроизведения или проверки. Отделяй подтверждённую ошибку
от предположения; нехватка измерений — отдельный пробел проверки.
Не выдавай предпочтение структуры за дефект без нарушенного правила проекта.
Review не даёт разрешения применять миграции, менять код или публиковать комментарии.

## Решение до PR

Для каждой таблицы требуй сценарий и инварианты, для каждого индекса — запрос,
распределение данных, существующие индексы и цену записи. Сравнивай планы на
сопоставимых данных. Не отклоняй sequential scan только за его название.
Проверяй tenant scope, параметризацию, N+1, лимиты, стабильную пагинацию,
изоляцию и порядок блокировок. Конкурентную ошибку доказывай расписанием двух транзакций.

Для миграции построй матрицу old/new schema × old/new application. Укажи,
какие сочетания реально возникают при deploy. Проверь duration/locks, backfill,
повтор, частичный сбой, cleanup и восстановление. Пустая БД не доказывает upgrade.
Отчёт должен различать локально проверенное и оценённое по документации.

Исполняемый код доступа к данным/мигратора проверяй по порогу 90% строк и ветвей;
DDL — тестами constraints, обновления схемы и данных, без выдуманного SQL coverage.
Результат: блокирующие дефекты, недостающие доказательства, остаточные риски.
Безопасность rollout не подтверждена, если неизвестны размер таблицы и механизм DDL.
