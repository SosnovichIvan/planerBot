# Frontend review

Найди дефекты, которые автору изменения имеет смысл исправить. Ревью само по
себе не разрешает исправлять исходники или публиковать комментарии в PR.
Skill самодостаточен и не требует frontend-engineering или дизайн-инструментов.

## Область и доказательства

1. Определи объект ревью: diff относительно указанной базы, рабочие изменения
   или названный модуль. Не придумывай base branch. Если база неизвестна,
   исследуй доступный код и явно обозначь ограничение сравнения.
2. Прочитай требования и конфигурацию изменяемого workspace. Для каждой
   существенной ветви проследи пользовательское действие через route/component,
   состояние, transport и отображение ответа. Проверь потребителей изменённых props.
3. Рассматривай подозрение как гипотезу: найди достижимый вход, последовательность
   действий и наблюдаемый результат. Проверь, не устраняет ли проблему router,
   query library, родительский компонент или штатный browser primitive.
4. Запусти узкую проверку, если окружение доступно. При недостатке инфраструктуры
   приведи обоснование по коду; не представляй его как выполненный runtime-тест.

## Проверяй по изменению

- Async UI: порядок ответов, отмена/игнорирование устаревшего запроса, unmount,
  cache keys с tenant/user/filter, invalidation, optimistic rollback и повтор submit.
- State: несколько источников истины, derived state в effects, stale closures,
  semantic keys при reorder, сохранение/сброс формы при смене объекта.
- Routing/rendering: direct URL, back/forward, URL-параметры, server/client
  boundary, hydration и серверные секреты. Не применяй SSR-правила к обычной SPA.
- Доступность: имя элемента, клавиатурная активация, focus, связь ошибки с полем,
  достижимость действий без pointer. Для сложного widget прочитай
  [interaction-review.md](references/interaction-review.md).
- Состояния и layout: loading/empty/error/success и узкий viewport, если изменены.
  Отличай дефект по коду от визуального предположения без рендера.
- Безопасность: путь недоверенных данных до HTML/URL sink, browser storage,
  раскрытие секретов; отсутствие UI-кнопки не доказывает серверную авторизацию.
- Производительность: связывай проблему с измерением либо явным ростом работы
  по размеру входа. Не требуй memoization для каждого компонента.

## Результат

Сначала замечания по убыванию влияния. Для каждого: приоритет, короткое название,
файл и узкий диапазон строк, условие возникновения, последствия, доказательство
и направление исправления. Используй шкалу проекта; иначе P1 — серьёзный дефект
основного сценария/изоляции данных, P2 — дефект при конкретном достижимом условии,
P3 — малое влияние. P0 оставь для подтверждённого безусловного блокера.

В diff-review отделяй внесённые дефекты от ранее существовавших. Не дублируй одну
причину по всем её проявлениям. Стилистические предпочтения и потенциальные
оптимизации без влияния не превращай в findings. Вопросы без доказательства
помещай в отдельные непроверенные риски.

Если подтверждённых замечаний нет, скажи это прямо; добавь область проверки,
выполненные тесты и ограничения. Не делай вывод «багов нет» из одного lint/build.

## Профиль правил проекта

Применяй [профильные правила](references/project-rules.md) только при явном согласии
на правила этого скилла в инструкциях проекта. При наличии approved snapshot
используй его; наличие файла само по себе не активирует правила. Они не запускают другие скиллы автоматически.
